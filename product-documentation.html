A conversational interface over NASA's Meteorite Landings dataset. Instead of handing people a map and a legend, this tool lets them point at something strange — a gap in central Africa, a cluster in Antarctica — and ask why, then watches the system actually go investigate.

01 — USE CASE

From map to explanation

Most meteorite distribution maps show where rocks were found, not where they actually fell — the difference is almost entirely a map of human search effort: population density, road access, vegetation, and which countries have funded expeditions. A raw scatter plot makes that bias invisible. This tool makes the bias the subject.

The workflow is intentionally short: see a pattern, select it, ask why, get an investigated answer with the evidence shown — not a static FAQ entry, a live query against the actual data.

→ 01

Notice

A sparse or dense region appears on the interactive map, filterable by year, class, mass, and fall type.

→ 02

Select

Draw a region directly on the map — no coordinates, no form fields.

→ 03

Ask

"Why are there so few here?" — plain language, no query syntax required.

→ 04

Investigate

The AI calls real tools against Postgres/PostGIS — population, climate, roads — and cites what it finds.

03 — FEATURES

What it actually does

Map

Interactive world map

Clustered meteorite points, filterable by year, class, mass, and fall vs. found, rendered from a live PostGIS-backed API.

Layers

Bias layer overlays

Toggle population, road density, climate, and land cover — the candidate explanations for search-effort bias, shown alongside the data they're meant to explain.

AI

"Explain This Pattern"

An agentic loop, not a canned prompt: the model decides which tools to call — population, climate, road density, a contrasting reference region — and shows its work, labeling each claim's confidence.

Score

Discovery Opportunity Score

Expected vs. observed finds per H3 hex cell, estimating how underexplored a region is relative to its population and accessibility — explicitly flagged as illustrative until calibrated against known search-heavy regions.

Off-world

Off-world finds, handled honestly

One meteorite in this dataset was found on Mars, not Earth. Rather than dropping it or plotting it at a nonsense coordinate, it's flagged and surfaced in its own panel.

04 — WHY THIS APPROACH

Decisions, and the data behind them

The raw NASA export looks clean until you actually query it. Pulling the real file surfaced exactly the kind of silent bias this product exists to expose — which became the argument for every architectural choice below.

Rows with coordinates exactly (0, 0) — NASA's placeholder for "unknown location," not a real spot in the Gulf of Guinea 6,214
Rows missing latitude/longitude entirely 7,315
Meteorite found on Mars by the Opportunity rover — a real, non-Earth coordinate, not bad data 1
Distinct meteorite classes (L6, H5, CM2…) — too many for a dropdown alone, hence searchable filtering 466

Three choices follow directly from this:

RATIONALE

Raw → dbt → marts, not a one-off script

Cleaning a dataset this quietly imperfect by hand in a script means the next person can't see what was assumed. Every transformation lives in version-controlled, tested SQL, with a visible audit trail of exactly which rows were dropped and why.

RATIONALE

Agentic tools, not a single prompt

A fixed "explain this" prompt re-derives the same shallow answer every time. Giving the model real tools — population lookups, a reference-region comparison — means the explanation is actually grounded in what it finds, with gaps stated as gaps.
